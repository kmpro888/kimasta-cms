## Summary

Implemented central SEO generation with derived defaults and stored overrides, XML
sitemap generation as a cached artifact, exact-lookup redirects with loop
protection, and breadcrumbs.

The acceptance criterion that shaped the design: **a theme cannot produce
conflicting canonical logic**, because the SEO service returns a finished
`SeoMeta` and the theme only prints it.

Executed by the controller directly; see `Wave-6-Tracking.md`.

## Database migrations

| Migration | Tables |
|---|---|
| `20261025000900_create_seo_tables.php` | `content_seo`, `redirects` |

Follows schema §27 and §35. SEO fields are **explicit columns**, not
`meta_key`/`meta_value` — the architecture rule that makes reading SEO one indexed
lookup. `redirects` has a unique `(site_id, source_path)` so lookup is exact and a
duplicate source is impossible at the storage layer. Verified forward and rollback.

## Events emitted

`settings.updated` and `theme.activated` are consumed by the cache, not emitted here.
SEO emits nothing of its own; the sitemap is invalidated by the content events the
cache layer already reacts to.

## Events consumed

None directly. The sitemap artifact is regenerated by a job, and the schema has no
event requirement for it in this wave.

---

## API changes

None. `/sitemap.xml` routing and the redirect middleware belong to the public
rendering layer.

---

## Cache impact

The sitemap is a generated artifact under
`storage/cache/system/sitemaps/sitemap-{siteId}.xml`. Serving it is a file read; it
is never rebuilt per request. Pages rendered through the theme declare
`settings:{siteId}` and `theme:{name}` dependencies, so an SEO settings change or a
theme switch evicts exactly the affected pages.

---

## Multisite impact

- All repositories are site-scoped.
- A content id from another site raises `CONTENT_NOT_FOUND`.
- SEO rows are per site: the same content on two sites can have different meta.
- Each site gets its own sitemap file.
- Each site has its own redirect table partition.

---

## Security impact

| Risk | Control |
|---|---|
| XSS through meta values | every interpolated value escaped in `render()` |
| XSS through JSON-LD | `</` escaped so user content cannot close the script tag (asserted) |
| Redirect to `javascript:` | scheme allowlist rejects it (asserted) |
| Protocol-relative redirect | rejected — it is an off-site redirect in disguise |
| Redirect loop | chain walk rejects self, two-step and longer cycles |
| Redirect write amplification | `hit_count` never incremented synchronously |
| Deleted featured image | `og:image` degrades to null instead of failing the page |

## Known limitations

1. **`sitemap-invalidation` is wired only at the service level.** `SitemapService::invalidate()`
   exists and is tested, but no listener currently calls it on content events —
   the sitemap regeneration job owns that, and the job runner is wired in
   `bin/cron.php` for publishing only. Registering a sitemap-rebuild job is a
   one-line addition at the next wave.
2. **Basic SEO scoring is not implemented.** The task pack lists it; it is analysis
   rather than core SEO, and no acceptance criterion depends on it.
3. No `hreflang`/multilingual alternates. The site model is single-locale per
   tenant in this wave.
4. Redirect `hit_count` is never written. Documented in the schema as optional and
   disabled by default; enabling it naively would add a write to every redirect.
5. Yoast mapping compatibility is a contract test placeholder only — there is no
   importer yet (Agent 15 owns migration).
