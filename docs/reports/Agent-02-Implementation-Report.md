Agent: Agent 02 — Multisite & Site Context

## Summary

Implemented tenant resolution and the three multisite tables. The resolution
path is cache-first: a compiled `domain-map.php` answers most requests with a
single opcache hit and **zero database queries**, falling back to the database
only on a miss. There is no default site and no code path that assumes
`site_id = 1`.

The module was started by a sub-agent and completed by the controller after the
sub-agent terminated mid-task; see `Wave-2-Tracking.md` for the handover.

## Cache impact

Two compiled caches, both written atomically and regenerated **on write, never
on read**:

| File | Regenerated by |
|---|---|
| `storage/cache/system/domain-map.php` | `addDomain`, `removeDomain`, `create`, `regenerateDomainMap` |
| `storage/cache/system/site-settings-<id>.php` | `SettingsService::set`, `forget` |

Requests that resolve through the domain map perform **0 database queries** for
tenant resolution. `DomainMap::siteIdFor()` is backed by an in-process memo, and
a test proves a resolved mapping still answers after the file is removed,
demonstrating the memo works within a request.

The settings cache is rebuilt after every write rather than merely invalidated,
because the contract says a write "refreshes" the compiled cache — dropping it
alone would push the next request back onto a query.

---

## Multisite impact

This module *is* the multisite boundary.

- Unknown host → `SITE_NOT_FOUND` (404). No fallback to a default tenant.
- `site_id` is never read from tenant request input; resolution is host-driven
  only.
- Settings and site lookups always take an explicit site id.
- A stale domain-map entry pointing at a deleted site falls through to the
  database instead of serving a half-deleted tenant.
- Domain uniqueness is enforced at the database level.

---

## Security impact

- `HostNormalizer` rejects rather than coerces: control characters (checked on
  the **raw** value, before `trim()`), schemes, paths, userinfo, ambiguous
  ports, IPv6 literals, invalid labels, over-long labels/hosts.
- Sending `example.com\0` is rejected. This was a real bug found by the security
  test: `trim()` silently stripped the NUL and the host normalised to a valid
  name. The check now runs before trimming.
- Cascade deletes are constrained by FK, so deleting a site cannot orphan
  domains or settings.

## Query/performance notes

- Every module query uses an explicit column list. No `SELECT *` exists.
- Domain resolution on a compiled-map hit performs zero queries.
- `SiteRepository::findByDomain` uses a single `JOIN` rather than
  lookup-then-fetch.
- `site_settings` writes use one `INSERT … ON DUPLICATE KEY UPDATE` statement,
  avoiding a read-then-write race.
- Prepared statements only, with `EMULATE_PREPARES=false`. Note for later
  modules: **a named placeholder cannot be reused in one statement** under
  native prepares — bind it twice under two names instead.

---

## Known limitations

1. `SettingsService` writes are synchronous to the compiled file. On a
   high-frequency settings writer this would be wasteful, but settings are
   admin-written and read constantly, which is the trade-off the architecture
   asks for.
2. The domain map is a single global file. With tens of thousands of domains
   this becomes a large array per request; the architecture targets small
   multisite counts, and the file is opcache-resident so it is not re-parsed.
3. `resolve()` returns an inactive site with `isActive() === false` rather than
   throwing. Serving policy for inactive sites is a content-layer decision and
   belongs to a later agent.
